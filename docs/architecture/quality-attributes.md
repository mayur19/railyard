# Quality attributes

Measurable targets for Railyard's non-functional requirements and how each target is (or will be) verified. Every target names a concrete verification artefact: an existing test file, or a backlog ticket from [../planning/backlog.md](../planning/backlog.md) that owns the benchmark or check. Targets marked **verified** have an automated test today; **partially verified** means the behaviour is tested but the number is not yet measured; **planned** means the ticket owns both.

Scenario identifiers (`QA-xx`) are local to this document; the corresponding NFR entries in `docs/product/requirements.md` reference them.

Reference environment for performance numbers: 4 vCPU, 8 GiB RAM, local SSD, PostgreSQL 15 on the same host, Node 22, `DATABASE_POOL_MAX=10`.

## 2. Performance scenarios in detail

### QA-01 Planning: 1000-job plan under 50 ms

Why the number: the planner runs inside the run-creation transaction while the project row is locked by `reserveRunNumber`. A slow planner directly extends the lock hold time and serialises run creation per project.

Budget breakdown (target, reference machine):

| Phase                                                  | Complexity                                       | Budget |
| ------------------------------------------------------ | ------------------------------------------------ | ------ |
| Matrix expansion + per-instance `if` evaluation        | O(Σ combinations × (axes + includes))            | 10 ms  |
| Implicit stage needs resolution                        | O(instances × jobs in previous stage) worst case | 10 ms  |
| `topologicalLevels` + `criticalPath` on instance graph | O(V + E) each                                    | 5 ms   |
| Interpolation of names, env, scripts                   | O(total template length)                         | 20 ms  |
| Slack                                                  |                                                  | 5 ms   |

Edge density is the risk: implicit stage needs connect every instance of stage _k_ to every instance of stage _k-1_. Two adjacent stages of 500 instances produce 250 000 edges. RY-149 must benchmark both a wide (two stages x 500) and a deep (1000-long chain) pipeline, and record results in CI as a non-blocking report with a blocking threshold at 2x budget.

### QA-03 / QA-04 Lease and pickup latency

The lease query is a CTE `SELECT id FROM jobs WHERE status='queued' ORDER BY queued_at, id FOR UPDATE SKIP LOCKED LIMIT 1` served by the partial index `jobs_queue_idx (queued_at, id) WHERE status = 'queued'`. Index size is proportional to queued rows only, so completed history does not slow leasing. RY-141 measures with 10 000 queued jobs across 200 runs and 50 runner processes on 2 hosts, reporting p50/p95/p99 of lease and of `completeJob`.

Pickup latency is dominated by polling (`RUNNER_POLL_MS`, default 1000 ms, minimum 50 ms). A runner that just finished a job polls again immediately (`runOnce` returns `true`), so a busy fleet drains the queue without poll delay.

### QA-05 / QA-06 Logs

End-to-end path: child stdout -> `LogWriter.write` -> masker -> buffer -> flush (every 250 ms, or immediately at 64 KiB) -> one `INSERT ... jsonb_to_recordset` + one `pg_notify` -> log hub -> `drain()` `SELECT ... WHERE seq > lastSeq LIMIT 500` -> SSE frame. Expected p95: 250 ms flush + ~10 ms DB + ~5 ms fan-out. Target < 1 s leaves headroom for proxy buffering, which nginx must disable.

Resume correctness rests on three facts verified by inspection of `sse.ts` and to be pinned by RY-066 tests:

1. The SSE handler subscribes to the hub **before** back-filling, so a chunk inserted between back-fill and subscribe still triggers a drain.
2. Every drain reads from the database with `seq > lastSeq` in a single promise chain, so frames are emitted exactly once and in order even if notifications arrive faster than queries.
3. Each `event: log` carries `id: <seq>`; the browser's `EventSource` sends `Last-Event-ID` on reconnect, which takes precedence over the `after` query parameter.

## 4. Known gaps against targets

- **Matrix size pre-check (fixed).** `checkMatrixSize` first computes an arithmetic upper bound (product of axis lengths plus include entries, `matrixUpperBound`) and refuses anything above 16x the 256-combination limit before materialising a single combination; `validate.test.ts` checks a 64^6 matrix is rejected in well under a second. RY-149 adds the remaining planner benchmarks.
- **Rate limits are per process** (`rate-limit.ts`). Stores are bounded (expired entries swept with a resumable cursor; when still full the active entry with the least time left is evicted and a warning logged), but counters are not shared, so they are correct only with one API process; RY-151.
- **Log fan-out** uses one LISTEN connection per API process but one `SELECT` per subscriber per notification. 500 viewers on one busy job means 500 queries per flush; batching is RY-066.
- **No resource limits on steps** beyond wall-clock timeouts: a step can exhaust memory or disk on the runner host until RY-054 (rlimits, cgroups v2 via `systemd-run`) and RY-057 (disk quotas).
- **Remote runners hold database credentials.** Acceptable for single-tenant self-hosting; RY-056 removes it.
