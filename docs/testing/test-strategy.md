# Test strategy

Railyard's risk is concentrated in four places: the pipeline compiler (validator, matrix, DAG, planner), the job state machine and run progression, the runner's concurrency with Postgres (leases, retries, reaping), and the live log path (masking, sequencing, SSE resume). The test suite is shaped around those risks rather than around layers: pure algorithms get exhaustive unit and property tests, everything that depends on Postgres row locks or LISTEN/NOTIFY is tested against a real Postgres, and the browser is covered by a thin component and smoke layer.

## 1. Pyramid

```
                 /\
                /  \        E2E (Playwright)            `e2e/smoke.spec.ts`: login -> project -> run graph; planned badges
               /----\       local only, skipped in CI
              /      \
             /  UI    \     React Testing Library        run graph, ANSI log view, login page   (apps/web/test)
            /----------\
           /            \   API integration (real PG)    HTTP via fastify.inject, runner end to end, migrations, SSE
          /  integration \                               (apps/api/test/*.http.test.ts, *.db.test.ts)
         /----------------\
        /                  \  Unit + property            shared domain logic, config, limiters, crypto, executor
       /   unit / property  \                            (packages/shared/test, apps/api/test/unit|executor)
      /______________________\
```

Approximate counts on `main`: about 120 test cases in `packages/shared` (11 files, several expanded further by `it.each` tables), about 70 in `apps/api` (7 suites). The shared suite needs no database and finishes in seconds; the API suite is dominated by real shell steps, short lease timeouts and per-suite schema resets.

Principles:

- **Domain logic is pure and lives in `packages/shared`**, so the hardest code is tested without I/O. Functions return new objects; tests assert the input was not mutated where that matters (`resolveBlockedJobs`).
- **No database mocks.** Anything involving SQL is tested against PostgreSQL, because the behaviour under test (SKIP LOCKED, row locks, transactional NOTIFY, unique-violation mapping, checksum verification) only exists in the real engine.
- **No HTTP server needed for API tests.** `fastify.inject` drives the full plugin chain (cookies, hooks, guards, error handler) in-process. Only the SSE suite listens on a real port, because it needs a streaming socket.
- **Real processes for the executor.** `runStep` tests spawn real `bash` processes, including process-group kills on timeout and abort.
- **Fix the code, not the test.** A flaky test is treated as a concurrency bug until proven otherwise.

### 2.2 Property-style tests

They use deterministic generators (fixed seeds or exhaustive enumeration), so a failure always reproduces; no property-testing library is needed.

| Property                                              | Generator                                                                                                                            | Oracle                                                                                                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Topological levels respect every edge and are minimal | 50 random DAGs of 5-64 nodes, edge probability 0.15, LCG seeded with 42                                                              | for every edge `dep -> node`, `level(dep) < level(node)`, and `level(node) = max(level(dep)) + 1` (0 for roots); every node appears exactly once |
| `nextRun` is correct                                  | 4 cron expressions mixing lists, steps, ranges, restricted day-of-month and day-of-week; 10 consecutive firings each from 2026-03-01 | a naive minute-by-minute scan over up to 400 days, re-implementing Vixie OR/AND day semantics independently                                      |
| Masking is independent of chunk boundaries            | the same text (secret repeated, adjacent, and a non-matching prefix at the end) split into chunks of every size from 1 to its length | output equals one-shot `maskSecrets`, and never contains the secret                                                                              |

Vitest with `jsdom`, 12 tests in three files. Network calls are stubbed at the `fetch` / context boundary; components are queried by role and label.

| File                  | Assertions                                                                                                                                                                                                                                                    |

### 2.5 `e2e/` (Playwright)

`e2e/playwright.config.ts` (invoked by `npm run test:e2e`) and one or two smoke specs (RY-008) drive a real browser against a running stack seeded with demo data. The smoke path is: log in as `owner@railyard.local`, open a seeded project, open a run and see its graph, open a job and see log output, and confirm that pending navigation items carry the "Planned" badge. The specs need the API, a runner and the Vite dev server plus an installed Chromium, so they run locally and are **skipped in CI**: the GitHub runner would download a browser on every build, and the integration suites already cover the same server behaviour.

## 3. Database integration tests

- **Real PostgreSQL 15+**, natively installed. No containers, no in-memory substitutes.
- Connection: `TEST_DATABASE_URL`, defaulting to `postgres://$USER@localhost/railyard_test?host=/tmp` (local Unix socket, current OS user, no password). Create it once with `createdb railyard_test`; `./run.sh test` creates it if missing.
- Isolation: each suite calls `freshDatabase()`, which runs `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` and applies every migration. The production guard in `resetSchema` makes this impossible against a `NODE_ENV=production` config, and tests never read `DATABASE_URL`.
- CI uses the PostgreSQL that ships on `ubuntu-latest`: `sudo systemctl start postgresql.service`, then a `railyard` role and `railyard_test` database are created with `sudo -u postgres psql` (see `.github/workflows/ci.yml`).
- Timeouts: 20 s per test, 30 s per hook, because runner suites execute real shell steps with short leases (`RUNNER_LEASE_SECONDS=5`, `RUNNER_POLL_MS=50`).

## 6. How to run

| Command                                                                                           | What it does                                                                                                                      |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `./run.sh test`                                                                                   | loads `.env`, installs deps if stale, creates the `TEST_DATABASE_URL` database (`railyard_test`) if missing, then runs `npm test` |
| `npm test`                                                                                        | same suites without the database bootstrap (`npm run test --workspaces --if-present`)                                             |
| `./run.sh check`                                                                                  | lint, `format:check`, typecheck, `./run.sh test`, production build: the local equivalent of CI                                    |
| `npm run test:coverage`                                                                           | suites with coverage thresholds (what CI runs)                                                                                    |
| `npm test -w @railyard/shared`                                                                    | only the pure domain tests (no database needed)                                                                                   |
| `npm test -w @railyard/api -- runner.db`                                                          | one API suite by file name filter                                                                                                 |
| `TEST_DATABASE_URL=postgres://railyard:pw@localhost:5432/railyard_test npm test -w @railyard/api` | point the API suites at a TCP Postgres                                                                                            |
| `./run.sh e2e`                                                                                    | runs `setup` (deps, `.env`, databases, migrations, seed), installs Playwright Chromium if missing, then `npm run test:e2e`        |

CI (`.github/workflows/ci.yml`) runs `npm ci`, lint, `format:check`, typecheck, `test:coverage` against the preinstalled Postgres, and the production build on every push to `main` and every pull request. E2E is not part of CI.

## 7. Adding tests for new tickets

- New domain logic goes into `packages/shared` with table-driven unit tests and, where an independent oracle exists, a deterministic property test.
- Every new route gets an integration test for the happy path, validation failure, 401, 403 (wrong role and missing CSRF where mutating) and tenant isolation. When a pending route is implemented, remove it from `PENDING_ROUTES`, flip `x-status` to `implemented` in `openapi.yaml` and add the route's own tests; the pending-route test keeps passing for the rest.
- Concurrency-sensitive changes (leasing, completion, scheduling) need a test that runs at least two actors at once against Postgres.
